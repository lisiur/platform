# 分类预填

## 分类预填：失效 id 的三态判定

- **场景**：任何按分类 id 预填默认值或解析历史记录的逻辑（记一笔默认分类、recents 解析、识别推荐、widget 绑定解析等）需要判断一个分类 id 当前是否可用。
- **症状**：用「id 是否存在」或「提交时刻有效」做判定，会把三类不可选分类放行：已删除（记录里查得到树里没有）、已归档（记录还在、网格不可选）、提交时是叶子后来新增了子分类变成父分类（父分类网格不可选）。预填会落到用户选不了的分类上。
- **原因**：可选分类树由 pickable 集合构建（不含归档），叶子集合再由树过滤父分类；分类树是随账本数据动态变化的结构，「曾经有效」不等于「现在有效」。
- **做法**：有效性判定一律以「能在当前类型的分类树里解析、且解析结果仍是叶子」为准；recents / 历史预填按序取第一个有效项，全部失效走回退链，不做存在性检查。

## 分类预填：默认值与快捷行数据源同源

- **场景**：同一份分类数据在界面有两处消费（默认预填 + 快捷入口行），要改其中一处的推导逻辑时。
- **症状**：两处各写一套推导（如默认值扫流水、快捷行读 recents），口径会漂移——用户最近一次提交用过的分类与打开 sheet 的默认值不一致；改动时也容易只改一处、漏掉另一处。
- **原因**：推导来源不同：流水扫描依赖服务端流水数据，recents 是设备本地提交记录，二者天然可能不同。
- **做法**：默认值推导与快捷行共用同一数据源与守卫（guard 条件一致）；推导逻辑提为纯函数、用单测锁定每一环；改默认逻辑时先核对快捷行行为是否需要同步。
