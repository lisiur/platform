# Explicit payer (paidBy) for journal entries

**Problem:** `JournalEntry.createdById` plays two roles — who recorded the entry and who fronted the money. When John pays $10 but Alice records it, settlement wrongly credits Alice.

**Fix:** add an explicit, editable payer (`paidById` → User) that defaults to the recorder. Every "who fronted the money" surface (project settlement `paidCents`, share-statement untagged fallback, settlement drill-down) switches from `createdById` to `paidById`; creator keeps meaning only "who recorded it". Semantics decisions baked in:

- Payer must be a current **ledger member** (validated like participants).
- Create: `paidByUserId` omitted/null → creator. Update: omitted → keep current payer (same keep-on-omit precedent as `countsInLedger`/`location`), explicit `null` → reset to creator, string → replace.
- Payer FK is `SetNull` like creator (account deletion keeps the entry; that entry then credits nobody).
- Untagged personal entries in the share-based statement flip from "creator bears all" to "payer bears all" — that's the whole point of the feature (John's $10 belongs to John's books, not Alice's).

## 1. Service — schema + migration (`packages/service`)

- `prisma/schema.prisma`:
  - `JournalEntry`: add `paidById String?` + `paidBy User? @relation("QianlaiJournalEntryPayer", fields: [paidById], references: [id], onDelete: SetNull)` with a comment mirroring the createdById one ("who actually fronted the money; defaults to the recorder; the recorder is not always the payer").
  - `User`: add back-relation `qianlaiPaidJournalEntries JournalEntry[] @relation("QianlaiJournalEntryPayer")` (next to line 41).
- New migration (`prisma migrate dev --name journal_entry_paid_by`, then edit before apply): `ADD COLUMN "paidById" TEXT`, FK → `user(id) ON DELETE SET NULL ON UPDATE CASCADE`, plus backfill `UPDATE qianlai_journal_entry SET "paidById" = "createdById" WHERE "createdById" IS NOT NULL;` so history attributes to the creator exactly as today. Regenerate client (`pnpm db:generate`).

## 2. Service — code

- `journal.repository.ts`:
  - `entryInclude`: add `paidBy` select (same shape as createdBy).
  - `createEntry` data/write: `paidById`.
  - `updateEntry`: accept optional `paidById` (write only when provided; creator stays untouched as today).
  - `listByProject`: select `paidById` (settlement input).
  - `listShareEntries`: where-clause branch 1 NOT → `{ paidById: viewerUserId }, countsInLedger: false`; branch 2 → `{ projectId: null, paidById: viewerUserId, countsInLedger: true }`; select `paidById` (drop `createdById`); doc comment "creator bears all" → payer.
  - `entryFilterWhere` `memberUserId` OR: add a `{ paidById: window.memberUserId }` branch (keep the createdById branch).
- `journal.service.ts`:
  - `createEntry`/`postEntryInTransaction`: new `paidByUserId` input; validate against `ledgerMembers` (reuse/extend the participant membership check), resolve to creator when absent; write `paidById`.
  - `updateEntry`: apply `paidByUserId` when present (`null` → creator id, omitted → keep `entry.paidById`); guest edit/delete guards stay keyed on `createdById` (record ownership ≠ payer).
  - `redactEntryCreatorEmail` (+ the `report.service.ts` copy): also null `paidBy.email` for non-owners.
- `project.service.ts` `projectReport`: `referencedUserIds` and `paidCents` attribution use `entry.paidById` (doc comment "the creator fronted it" → payer).
- `report.service.ts`: `ShareEntry` + `paidById`; `viewerShareCents` untagged fallback → `[entry.paidById ?? viewerUserId]`.
- `routes/journal-entry/schema.ts`: request `paidByUserId: z.string().min(1).nullable().optional()` (document the create/update semantics); response `paidById` + `paidBy {id,name,email,avatar}` nullable; `serializeEntry` bound + pass-through; `memberUserId` query doc mentions "entries they paid for".
